# Agent guide

Instructions for AI coding agents (and humans) working in this repo. Follow the existing
patterns: the `workouts` feature shows every layer, so copy its shape for new features.
The README explains the setup; this file is the working rules.

## Getting set up

```sh
pnpm install && pnpm bootstrap   # .env, Postgres in Docker, migrations, test browser
```

`pnpm bootstrap` is safe to rerun and says exactly what is missing (e.g. Docker not running).
pnpm runs every script on the Node version pinned in `package.json` (`devEngines`),
downloading it if needed, so the machine's own Node version doesn't matter.

## Definition of done

A change is done when **`pnpm check` and `pnpm e2e` pass** and:

- new behaviour has tests (API: Supertest in `apps/api/test`; web: Vitest + Testing Library;
  user flows: Playwright in `apps/e2e/tests`)
- new UI components have a Storybook story next to them (`*.stories.tsx`); stories run as tests
- UI changes are checked visually: look at the screenshots `pnpm e2e` saves in
  `apps/e2e/screenshots/`
- any change to `packages/db/src/contract.prisma` has an emitted contract and a planned migration
- new environment variables are in `.env.example`, validated in config, and, if production
  needs them, set in `infra/vercel.tf`

## Commands

```sh
pnpm check                                    # typecheck, lint, format, unit/API/story tests
pnpm e2e                                      # end-to-end tests in a real browser
pnpm e2e tests/workouts.spec.ts               # one e2e file (run from apps/e2e)
pnpm typecheck | pnpm lint | pnpm format | pnpm test
pnpm --filter @app/api test                   # one package's tests
pnpm --filter @app/db emit                    # after editing contract.prisma
pnpm --filter @app/db migration:plan --name <slug>
pnpm db:migrate                               # apply migrations to DATABASE_URL
cd apps/web && pnpm dlx shadcn@latest add <name>  # add a shadcn/ui component
```

## Verifying your change

Prove it works with the commands, don't assume. What each one proves:

| Command      | Proves                                                                                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm check` | types, lint/architecture rules, formatting; API behaviour against Postgres; components; every Storybook story renders, passes its `play` test and has no accessibility violations |
| `pnpm e2e`   | the real web app + API + database work together in Chromium, with no browser console errors                                                                                       |

`pnpm e2e` starts its own API (port 3100) and web app (port 5174) against the test database,
so it works whether or not `pnpm dev` is running. For a new user-facing feature, add a spec
that walks the main flow, call `capture('<name>')` at the key states, and look at the saved
screenshots before calling the work done. To debug a failing e2e test, rerun it with
`--trace on` and read the error context Playwright prints.

## Architecture rules

Enforced by ESLint (`eslint.config.ts`). Don't work around them; restructure instead.

- **API:** route handlers → services → database. `*.routes.ts` must not import `@app/db`.
  `*.service.ts` must not import `express`. Only `app.ts` wires services to routers.
- **Web:** browser code may only import `@app/shared` from the workspace. All HTTP goes
  through `apiRequest` in `@/lib/api` (no direct `fetch`). Route files import only their page
  and query options. Pages and components live outside `routes/`.
- **Shared:** `@app/shared` depends only on `zod`.
- **Workspace imports** use package names (`@app/shared`), never relative paths into another
  package.

Not enforced by tooling, so check yourself:

- Request/response shapes are defined once in `@app/shared` and used on both sides: the API
  validates input with `validate(Schema, input)`, the web validates responses via
  `apiRequest(path, Schema)` and forms via TanStack Form `validators: { onSubmit: Schema }`.
- Expected failures throw `HttpError` (or `notFound()`); never send error JSON by hand.
- **Data is per user.** Every table holding user data has `userId`. Services take the acting
  user's ID as their first argument and filter every query by it; handlers get it from
  `currentUserId(req)` (REST) or the MCP server's `userId`. Another user's row is a 404, never
  a 403. Only `/health`, MCP discovery and dev sign-in are public.
- **MCP tools** mirror the REST API: same services, same shared schemas as `inputSchema`. A
  feature an AI assistant should use gets tools in `features/mcp/mcp.tools.ts` and tests in
  `apps/api/test/mcp.test.ts` (connect a real MCP client as a unique user).
- Services return plain shared types (`Workout`, `Exercise`), converting timestamps with
  `toISOString()` and decimals (stored as text by Prisma) with `Number()`.

## Workout domain rules

- **Units and effort:** weights are pounds (`weightLb`, null = bodyweight / no added load).
  Effort is stored as RPE; inputs may give RIR instead (RPE = 10 − RIR), never both.
- **Dates:** workouts have a calendar `date` (YYYY-MM-DD) in the user's time zone
  (`APP_TIMEZONE`). Use `localDate`, `weekStart`, `addDays` from `apps/api/src/lib/training.ts`;
  never derive dates from UTC timestamps. Weeks start Monday.
- **Calculations** live in `lib/training.ts` and the stats service: estimated 1RM is Epley
  (`estimateOneRepMax`); warm-up sets never count toward volume, records or estimates.
- **Exercise names** go through `exercises.resolve()` / `lookup()` (normalization in
  `lib/exercise-names.ts`), never raw string comparison. Names met while logging create
  _unconfirmed_ exercises with suggestions; names in a saved routine are confirmed. Merging moves
  sets and routine entries and turns the old name into an alias.
- **Routines are versioned:** saving a changed plan adds an immutable `RoutineVersion` (with a
  change note); identical plans add nothing. Workouts link the version they followed. One-day
  tweaks are not versions.
- **Ownership:** `Exercise`, `Routine`, `Workout` and `WorkoutSet` carry `userId`; routine
  versions and their exercises are reached only through an owned routine.
- **Claude is the main interface.** Every capability has an MCP tool with a description that
  teaches the workflow (plan → log → review new names). Changing behaviour means updating the
  tool descriptions and server instructions too.

## Adding a feature (end to end)

1. **Contract:** add the model to `packages/db/src/contract.prisma`, then
   `pnpm --filter @app/db emit` and `pnpm --filter @app/db migration:plan --name <slug>`,
   then `pnpm db:migrate`.
2. **Shared schemas:** `packages/shared/src/<name>.ts` (entity, create/update input, params);
   export from `index.ts`.
3. **Service:** `apps/api/src/features/<name>/<name>.service.ts`: `create<Name>Service(db)`.
4. **Routes:** `<name>.routes.ts`: `<name>Router(service)`; validate every input; pass
   `currentUserId(req)` to the service. If AI assistants should use it, add MCP tools too.
5. **Wire up** in `apps/api/src/app.ts`.
6. **API tests:** `apps/api/test/<name>.test.ts` (see the testing rules below).
7. **Queries:** `apps/web/src/features/<name>/queries.ts` (query options + mutations that
   invalidate their queries).
8. **UI:** feature components and forms in `features/<name>/`, each with a story; page in
   `src/pages/<name>-page.tsx`.
9. **Route:** `src/routes/<path>.tsx` with a `loader` that calls `ensureQueryData`, and a nav
   link in `components/root-layout.tsx` if needed.
10. **End-to-end:** `apps/e2e/tests/<name>.spec.ts` walking the main user flow, with
    `capture()` at key states.
11. `pnpm check` and `pnpm e2e`, then review the screenshots.

## Code rules

- **TypeScript in Node runs via type stripping.** Only erasable syntax: no `enum`,
  `namespace`, or constructor parameter properties (assign fields in the constructor). Use
  unions or `as const` objects. Relative imports in Node code end in `.ts`. Web code uses
  extensionless imports and the `@/` alias.
- **No `.js` files.** Configs and scripts are TypeScript.
- **Use `pnpm exec <tool>`, never `npx`/`npm`.** npm can't satisfy the pinned Node version
  (`devEngines`) and errors out on machines with an older Node.
- **No unused code and no escape hatches.** ESLint rejects `_`-prefixed unused names,
  `@ts-ignore`/`@ts-expect-error`/`@ts-nocheck` and explicit `any`, and ignores
  `eslint-disable` comments entirely. If a type assertion is truly unavoidable (a third-party
  typing bug), keep it narrow and comment why.
- **Dependencies:** pin exact versions (`saveExact` is on). A dependency used by several
  workspace packages goes in the `catalog` in `pnpm-workspace.yaml` and is referenced as
  `"catalog:"`. Check that a package is the current recommended one before adding it. New
  install scripts must be approved explicitly (`allowBuilds`).
- **Environment variables:** API: add to the Zod schema in `apps/api/src/config.ts`. Web: only
  `VITE_*`, typed in `src/vite-env.d.ts`, read via `src/lib/env.ts`. Always add to
  `.env.example`.
- **UI:** use shadcn/ui components and Tailwind theme tokens (`bg-background`,
  `text-muted-foreground`, `--chart-1`), not raw colours. Keep components accessible
  (labels, `aria-*`); Storybook's accessibility panel flags problems in stories.

## Testing rules

API tests share one database and **run in parallel, with no cleanup**. Every test must:

- act as its own user: `uniqueUserId()` and `bearer(userId)` from `test/helpers.ts`, so
  per-user data never collides
- create the rows it needs, with unique values: `unique('label')` from `test/helpers.ts`
- assert only on its own data. Because each test is a fresh user, exact assertions on that
  user's lists, counts and summaries are safe; across users, only `toContainEqual` /
  `not.toContain`
- never update or delete rows it didn't create

Queries whose order tests rely on need a deterministic tie-breaker (e.g. `createdAt`, then
`id`).

End-to-end tests follow the same rules (they share the test database and run in parallel):
every test is automatically signed in as its own fresh user (`user` fixture; opt out with
`test.use({ signedIn: false })`), use `unique()` for names, set up data with the `api` fixture
(an HTTP client authorized as that user) and test the behaviour through the UI. Import `test`/`expect` from `./fixtures.ts`, never from
`@playwright/test` directly: the fixture fails any test whose page logs a console error. Find
elements the way users do (`getByRole`, `getByLabel`, `getByText`); if that's impossible, the
UI probably has an accessibility gap to fix.

Web tests are colocated (`*.test.ts(x)`) and test components through what users see
(roles, labels, text).

## Library notes (APIs newer than most training data)

**Library skills.** Prisma 8 (`@prisma/orm-postgres`), TanStack Router, its Vite plugin and
TanStack Charts ship agent skills written for the exact installed version. `pnpm install`
links them into `.claude/skills/` (Claude Code loads them automatically; the links are not
committed). Other agents can read the same files at `node_modules/<package>/skills/`. When a
skill and your memory disagree, the skill wins. The Prisma _Platform_ skill (`prisma`
package) is deliberately declined: we host on Vercel and Neon, not Prisma's platform.

- **Prisma ORM 8 (RC)** is not Prisma 5/6/7. The schema is a "contract"
  (`contract.prisma`, first line `// use prisma-8`). Queries use the collection API:
  `db.orm.public.Item.where({ id }).first()`, `.orderBy([(i) => i.createdAt.desc(), ...])`,
  `.limit(n).all()`, `.create({...})`, `.where({ id }).delete()` (returns the row or `null`).
  Bulk deletes require an explicit filter: `.where((i) => i.id.gt(0)).deleteAll()`.
  There is no `findMany`/`findUnique`. Look at `node_modules/@prisma/orm-*` typings when
  unsure.
- **TanStack Charts** is `@tanstack/charts` (with `@tanstack/charts/react`), not
  `@tanstack/react-charts` (now a compatibility package). Charts are `defineChart({ marks,
scales })`; pass a configured scale instance (`scaleLinear().domain([0, max])`) to fix a
  domain.
- **Sentry 11:** logs and metrics are on by default (no `enableLogs`). `sendDefaultPii` was
  replaced by `dataCollection`. Custom metrics: `Sentry.metrics.count(name, value)`.
- **pnpm 12:** install scripts and packages' AI-agent skills need explicit approval
  (`allowBuilds`, `permissions` in `pnpm-workspace.yaml`); review a package's `skills/`
  folder before approving it. Node 26 doesn't bundle corepack.
- **TypeScript 7** (`typescript7` alias) runs `pnpm typecheck`; the `typescript` package is
  6.x because ESLint and Storybook need its compiler API.
- **MCP TypeScript SDK v2** is split into `@modelcontextprotocol/server`, `/express`, `/node`
  and `/client` (not the v1 `@modelcontextprotocol/sdk`). Tools: `server.registerTool(name,
{ inputSchema: zodObject, outputSchema }, handler)`; auth: `requireBearerAuth` and
  `mcpAuthMetadataRouter` from `/express`.
- **WorkOS AuthKit:** web tokens are issued by `https://api.workos.com` (check `client_id`);
  MCP tokens by the AuthKit domain (check `aud` = MCP URL, reject `sub_profile: ai_agent`).
  See `apps/api/src/auth/tokens.ts`.
- **shadcn/ui** components import `cn` from the `cn` package (shadcn's replacement for
  clsx + tailwind-merge).

## Claude Code

In Claude Code cloud sessions Docker is installed but its daemon isn't started:
run `(dockerd > /tmp/dockerd.log 2>&1 &)` before `pnpm bootstrap` (it tells you if needed).

`.claude/settings.json` runs `.claude/hooks/format-and-lint.ts` after every file edit:
Prettier formats the file and ESLint reports remaining problems back immediately. Fix what
it reports before moving on.
